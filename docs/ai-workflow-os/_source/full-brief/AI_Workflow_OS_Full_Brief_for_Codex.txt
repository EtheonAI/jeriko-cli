1. Executive Summary
AI Workflow OS is a new architecture for autonomous AI workflows. The product is not a chatbot, not a visual node builder, not a generic agent framework, and not a Manus clone. The product is a .flow-based runtime where the AI writes a persistent workflow operating file and the platform executes it safely, repeatedly, and observably.
Main AI / Compiler: understands the user goal and creates or updates the .flow file.
Runtime: executes the compiled .flow through Inngest and deterministic handlers.
Workers/Subagents: perform scoped tasks such as research, writing, image generation, coding, verification, analytics, and memory patches.
Tool Router: calls apps through Composio or direct APIs while enforcing permissions and approvals.
Vercel Sandbox: runs generated code and file-processing scripts safely outside production.
Event Context Layer: routes structured context between tasks, workflows, apps, workers, and the main AI only when needed.
UX: chat for commands and a side panel for live workflow operations.
The key product behavior: the workflow is workflow-aware, task-aware, event-aware, failure-aware, permission-aware, and improvement-aware. It can continue when optional tasks fail, raise issue cards, ask approval before risky actions, and propose patches after runs.

4. Business Thesis and Target Users
The business thesis is that people want autonomous work done, but current options are either too manual, too expensive, too black-box, too developer-heavy, or too brittle. The product should start focused, then expand horizontally once the runtime proves reliable.
Initial wedge: founders, operators, agencies, solo developers, SMB teams who want recurring workflows without building nodes.
Best early workflows: social/content operations, inbox drafting, lead generation, competitor monitoring, inventory/email/CRM workflows, weekly reports.

5. The .flow Operating File
.flow is a restricted YAML-like instruction file. The AI writes it, the platform parses and validates it, then the compiler converts it into runtime JSON. The runtime executes JSON, not raw text. The file extension gives the product identity, while the syntax stays AI-friendly.
Restricted YAML-like surface syntax.
Own vocabulary: goal, triggers, jobs, tasks, imports, permissions, tools, if_fail, emit, reflection, budget.
Reject unsafe YAML features such as anchors, aliases, custom tags, multi-document YAML, unknown keys, unbounded loops, and external actions without approval.
Use imported .md files for deep instructions: brand.md, memory.md, writer.md, platform.md, validation.md.
Use scripts/ for deterministic custom code and artifacts/ for outputs.
flow: "0.1"
name: social_media_manager

goal: |
  Create daily social posts, generate image assets,
  ask approval before publishing, track analytics,
  and improve weekly.

imports:
  brand: brand.md
  writer: instructions/writer.md
  image: instructions/image.md
  instagram: instructions/instagram.md

permissions:
  auto:
    - read_public_web
    - create_drafts
    - write_internal_files
    - run_sandbox_code
  ask:
    - publish_social_post
    - send_email
    - update_external_system
  block:
    - delete_data
    - transfer_money
    - expose_secrets
    - change_security_settings

jobs:
  daily_content:
    trigger:
      type: schedule
      cron: "0 10 * * MON-FRI"
    tasks:
      - id: research_topics
        type: ai_task
        worker: researcher
        uses: [web.search, web.read]
        output: [artifacts/trends.json]
        required: false
        if_fail: continue_degraded
        emit: research.completed

      - id: validate_posts
        type: sandbox_command
        run: python scripts/validate_posts.py
        input: [artifacts/posts/, brand.md, memory.md]
        output: [artifacts/validation_report.json]
        if_fail: regenerate_once_then_ask

6. Full Runtime Lifecycle
User prompt: User describes the desired work in chat.
Compile: Main AI creates workflow.flow, imports, and optionally generated scripts.
Parse: The .flow parser loads the restricted YAML-like file.
Validate: Structural and semantic validators check fields, references, tools, permissions, budgets, cycles, and bounded loops.
Compile to runtime JSON: The normalized spec is stored as compiled_json.
Trigger: Manual, schedule, webhook, app event, workflow event, or approval event starts a run.
Execute: Inngest generic executor dispatches each task by type.
Report: Each worker emits TaskReport, EventContextPacket, artifacts, and usage events.
Display: Side panel streams events, tasks, artifacts, approvals, issues, and cost.
Reflect: When configured triggers fire, a Run Reflection Packet is sent to the main AI.
Patch: Main AI proposes FlowPatch, memory patch, instruction patch, or worker-routing update.
Version: Accepted patches create a new workflow version. Running runs keep their original version.

8. Event Context Layer
The Event Context Layer is how apps, workflows, tasks, subagents, and the main AI share state without freeform agent chat. It is internal at first; it can become an ECP-style public/internal protocol later.
EventContextPacket
{
  id: "ecp_123",
  type: "artifact.image.generated",
  workflow_id: "wf_social",
  run_id: "run_456",
  job_id: "daily_content",
  task_id: "generate_images",
  worker_id: "image_worker",
  correlation_id: "corr_daily_2026_05_22",
  causation_id: "event_post_draft_ready",
  summary: "Generated Instagram and LinkedIn image assets.",
  payload: { platforms: ["instagram", "linkedin"], approval_required: true },
  artifacts: [
    { path: "artifacts/images/instagram.png", related: "artifacts/posts/instagram.json" }
  ],
  quality: { confidence: 0.88, verifier_status: "passed" },
  routing: { notify_tasks: ["approval", "publish"], notify_main_ai: false },
  cost: { credits: 8 }
}

Workers do not freely chat with each other by default.
Workers emit typed events and task reports.
Context Router stores and routes events to dependent tasks/workflows/UI/main AI based on .flow rules.
Main AI receives compressed reflection only when needed, not every raw event.

10. Inngest, Vercel Sandbox, Tools, and App Integrations
Inngest is the durable execution substrate. It handles runs, retries, waits, signals, events, sub-workflows, schedules, concurrency, and monitoring. The product does not create custom Inngest functions per customer workflow; it creates a small set of reusable platform functions and one generic executor.

Vercel Sandbox

tool/app execution for Gmail, Slack, Shopify, Stripe, Twilio, social platforms, CRM, analytics

Generic executor model:
workflow.run.requested
  → load compiled_json
  → create run
  → resolve runnable tasks
  → dispatch by type:
      ai_task          → modelRouter.run()
      tool_call        → toolRouter.execute()
      sandbox_command  → sandboxRunner.run()
      human_review     → approvalRunner.wait()
      wait_for_event   → eventRunner.wait()
      foreach/parallel → controlled fan-out
      memory_patch     → patchWorker.propose()
  → store reports/events/artifacts
  → finalize or pause

11. Custom Code Execution
User workflows can include custom code, but the code is never deployed to production. It is saved as versioned workflow files and executed only in Vercel Sandbox.
Generated scripts: scripts/generated/scraper.py, validate_csv.py, aggregate_metrics.py, validate_posts.py.
Storage: script source stored in workflow_files and object storage with version, hash, creator, approval status.
Execution: sandbox_command stages declared inputs and scripts, runs command with limits, captures stdout/stderr, saves declared outputs.
Security: no OAuth tokens in sandbox; network disabled unless allowed; dangerous commands blocked; time and output size limits.

14. Billing, Credits, Cost Control, and Limits
Autonomous workflows can run many events, crons, apps, workers, and scripts. Billing and rate limiting must be core, not an afterthought.
Charge by subscription plus workflow credits.
Meter model tokens, image generation, tool calls, sandbox seconds, search calls, storage/artifacts, and event volume above limits.
Every workflow has per-run, per-day, and per-month budgets.
Before each task, estimate cost and check remaining budget and org credits.
If budget is exceeded, pause and ask, or fail safely according to .flow policy.
Never offer unlimited autonomous workflows.
budget:
  max_credits_per_run: 50
  max_credits_per_day: 200
  max_runtime_minutes: 45
  max_tool_calls: 100
  max_sandbox_seconds: 300
  max_ai_tasks: 20
  on_exceed: pause_and_ask

15. Security, Permissions, and Safety
Permission model: auto, ask, block.
External actions: send email, publish post, update CRM, post Slack, create calendar invite require approval by default.
Blocked by default: delete data, transfer money, expose secrets, change security settings, create fake accounts, bypass bot protection.
Tool calls: validate args, enforce connected scopes, idempotency keys, approvals, logs.
Sandbox: no OAuth tokens, limited files, timeout, network policy, dangerous command scanner, output limits.
Event ingestion: verify signatures, dedupe IDs, rate-limit sources, pause on event storms.
Prompt/tool safety: treat external content as untrusted; tool use must pass runtime permissions, not model suggestions.

19. Open Questions and Final Notes
Should .flow v0 use a YAML parser plus validator first, or a hand-written tolerant parser immediately? Recommendation: YAML-compatible parser first for speed, custom tolerant parser after proof.
What expression language should be used for ${...}? Recommendation: tiny custom subset first, not full CEL/JMESPath initially.
Which tools should be direct APIs versus Composio? Recommendation: direct for Gmail/Slack/Stripe/Shopify if needed; Composio for breadth.
How much should main AI see? Recommendation: only creation, repair, user questions, and reflection packets triggered by rules.
What is the first workflow proof? Recommendation: social content operator with image worker, scheduler, approval, issue card, and reflection patch.
Final guiding principle: The workflow is the product. The .flow file is the AI operating contract. The runtime executes deterministically where possible. Events move context. Workers report. Issues surface. Reflection improves. Users stay in control through approvals, notifications, side panels, versioning, and sharing.
